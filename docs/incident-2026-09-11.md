# Post-mortem: unattended driver upgrade broke CUDA

**Date:** 2026-09-11
**Impact:** No new CUDA process could start. An already-running vLLM server
kept serving.
**Detection:** By symptom, when a new process failed to initialise.

## What happened

`unattended-upgrades` moved the NVIDIA driver from 595.84 to 595.91.07. The
upgrade ran DKMS, which rebuilt the stock modules and installed them over the
patched `nvidia.ko` files for kernels 5.15.0-190 and -191.

The result was a split system:

- **Userspace** at 595.91.07, from the new package.
- **Loaded kernel module** still 595.84, because nothing had rebooted.

CUDA refuses to initialise when these disagree:

```
Failed to initialize NVML: Driver/library version mismatch
```

The running vLLM survived only because it already held an open CUDA context
from before the upgrade. Every new process failed. P2P was gone too, since the
newly installed modules were stock.

## Why it was not caught earlier

Two separate gaps, and the second one hid for months.

The existing protection was a `postinst.d` hook that rebuilds the patched
driver **when the kernel changes**. That was written after an earlier incident
in the 5.15.0-187 to -190 jump, where new kernel modules silently reverted to
stock and P2P was off for roughly three months before anyone noticed.

A **driver** upgrade is a different trigger and the hook does not fire on it.
The failure mode is also worse: a kernel upgrade leaves you with a coherent
stock driver and merely no P2P, whereas a driver upgrade leaves the module and
userspace mismatched and CUDA does not run at all.

The common root cause is that DKMS owns `/lib/modules/*/updates/dkms/` and
will overwrite anything placed there, while the patched build lives outside
DKMS in a separate tree.

## Why the patched build is not in DKMS

DKMS invokes `make` inside `kernel-open/`, which skips the top-level Makefile
that creates this symlink:

```
kernel-open/nvidia/nv-kernel.o_binary -> ../../src/nvidia/_out/Linux_x86_64/nv-kernel.o
```

That 17.6 MB blob is the Resource Manager containing the P2P changes. Without
it the link silently succeeds and produces an ~18 MB module with no P2P
instead of the correct ~33 MB one. A DKMS-driven build of this tree is
therefore not just unsupported, it fails quietly.

## Fix applied

A version guard was added to the hook. Before installing anything it compares
the patch tree version against the installed userspace:

```sh
TREE_VER=$(sed -n 's/^NVIDIA_VERSION *= *//p' "$SRC/version.mk" | head -1)
USER_VER=$(ls /usr/lib/x86_64-linux-gnu/libcuda.so.* \
             | grep -v 'so\.1$' | sed 's|.*libcuda\.so\.||' | head -1)
```

If they differ, the hook installs nothing and logs that the patch needs porting.
The reasoning: a stock driver that matches userspace costs P2P, while a patched
driver that does not match userspace costs all GPU access. Prefer coherent and
slow over broken.

A size gate was added for the same class of silent failure:

```sh
MIN_SIZE=30000000   # patched is ~33 MB; stock is ~18.7 MB
```

The patch was then ported to 595.91.07 and the tree rebuilt, which is the
state the repository documents.

## What is still not fixed

**Driver upgrades remain unhandled.** The hook is a kernel `postinst.d` hook
and there is no equivalent trigger wired for driver package upgrades. The
version guard means the next unattended driver bump degrades safely rather
than catastrophically, but it still degrades: P2P turns off and stays off
until someone ports the patch.

Nothing currently prevents that upgrade from happening:

```
$ apt-mark showhold
(empty)

$ grep -A2 Package-Blacklist /etc/apt/apt.conf.d/50unattended-upgrades
Unattended-Upgrade::Package-Blacklist {
};
```

And the package is reachable from an allowed origin:

```
$ apt-cache policy nvidia-dkms-595-open
  Candidate: 595.91.07-0ubuntu0.22.04.1
     500 http://archive.ubuntu.com/ubuntu jammy-updates/multiverse amd64
```

The proposed remediation is in `operations.md`. It is not yet applied.

## Lessons

1. **A silent degradation needs an alarm, not just a repair.** The 187-to-190
   loss went unnoticed for months because nothing checked that P2P was on. An
   alarm was added afterwards: `check-nvidia-p2p` gates on both the on-disk
   module size and the runtime peer matrix, and a state-gated Uptime Kuma push
   monitor reports the P2P state rather than whether the script ran.
2. **Guard the version pair, not just the build.** Module and userspace are a
   matched pair. Any automation that can install one must check the other.
3. **Fix the trigger you were bitten by, then ask what other triggers exist.**
   The kernel hook was a correct response to the first incident and a complete
   answer to the wrong question.
